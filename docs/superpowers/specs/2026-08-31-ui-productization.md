# 明亮童话志怪 UI 产品化规格

**状态：** Accepted  
**日期：** 2026-08-31  
**实施顺序：** 仅按 [U0–U11 路线图](../plans/2026-08-31-ui-productization-roadmap.md) 推进；一次只做一个阶段。  
**架构决策：** [ADR-0001](../../adr/0001-ui-presentation-shell.md)。

本文件是全界面产品化的验收真源。玩法规则与数值仍以既有规格为准；本规格不新增玩法、不改存档语义。视觉名统一为“明亮童话志怪”：浅底、圆角、彩色描边、角色中心、少数大色与清楚层级。

## 1. 目标与非目标

### 1.1 目标

1. 全部产品页面具备一致的正常、`loading`、`empty`、`error`、`locked` 呈现契约。
2. 以竖屏 `750×1334` 为主设计画布，同时保证横屏可完成全部任务。
3. 标题大厅、初始选择、战斗主界面通过三关键帧门后才进入批量页面制作。
4. Cocos Creator 3.8.2 的实际运行截图、最终构建和真机指标是验收证据真源。
5. 微信与抖音小游戏最终产物的主包分别不超过 `4 MiB`（`4,194,304` 字节）。
6. 在不改 `packages/core` 玩法职责的前提下，建立 presentation 与 AppShell 边界。

### 1.2 非目标

- 不新增模式、精怪、术法、数值或付费系统。
- 不改局内流程、存档格式、服务端协议与随机性。
- 不换引擎，不复制任何第三方角色、素材、文案、具体布局或动效时间线。
- 不把静态稿、SVG、浏览器替身、平台占位包或 `.shots` 当作实际 Cocos 证据。

## 2. 真源与冲突优先级

1. 页面代码事实源：`packages/core/src/ui/screens.ts` 的 `LOBBY_SCREENS`、`RUN_SCREENS`，以及 `packages/core/src/ui/tour.ts` 的 `TOUR`。
2. 产品状态与验收：本规格。
3. 架构边界：ADR-0001。
4. 阶段顺序：U0–U11 路线图及开工前独立编写的阶段细计划。
5. 视觉观察只能来自 [clean-room 参考矩阵](../../ui/reference-matrix.md) 中的公开 URL；观察不得覆盖原创约束。

若代码新增页面，必须先更新页面矩阵与本规格，再安排到尚未开工的 U 阶段。不得以“导览暂时到不了”为由删除页面；当前 `party` 即属此类。

## 3. 页面全集

### 3.1 页面与主任务

下表覆盖 19 个代码页面、5 个导览子界面，并将 `codex` 的列表/详情拆成两个产品体验面，共 25 个产品面。`loading` 与 `error` 对所有行强制适用；“空态/锁定”列定义该页的语义，没有自然空态或门槛的页面也必须在状态注入测试中安全降级，不得白屏或卡死。

| 产品面 | 代码/导览映射 | 主任务 | `empty` | `locked` |
|---|---|---|---|---|
| 标题大厅 | `title` | 开始旅途，进入次级入口 | 无可恢复存档时仍显示“新的旅途” | 联机入口不可用时说明原因，本地旅途不受影响 |
| 模式选择 | `mode` | 查看差异并选择模式 | 无模式属于数据错误，转 `error` | 未达条件的模式保留可见并说明条件 |
| 设置 | `settings` | 调整声音、动效与可访问选项 | 无持久化值时使用明确默认值 | 平台不支持的选项禁用并解释 |
| 契录列表 | `codex` / `codex-list` | 浏览、筛选已知精怪 | 尚无记录时给出获得路径与返回 | 未知条目显示轮廓和解锁条件 |
| 契录详情 | `codex` / `codex-entry` | 阅读已知精怪资料 | 条目缺失转 `error` 并可回列表 | 未解锁字段隐藏内容并说明条件 |
| 卵房 | `eggs` | 查看可孵化内容和资源 | 无可孵化项时解释获得途径 | 资源或进度不足时显示条件 |
| 成就 | `achievements` | 查看目标与领取状态 | 无成就数据时可重试 | 未达成项显示进度，不隐藏目标 |
| 统计 | `stats` | 查看旅途汇总 | 无历史时展示零值说明 | 受条件限制的统计说明解锁方式 |
| 存档 | `slots` | 读取、创建、管理存档 | 无存档时突出“创建” | 不可覆盖或云端不可用时说明原因 |
| 名词页 | `glossary` | 查询原创术语 | 无条目属于数据错误，转 `error` | 无自然锁定；注入时显示只读说明 |
| 初始选择 | `starter` | 比较三只初始精怪并确认 | 候选缺失转 `error`，禁止空确认 | 条件不足的候选可见并说明条件 |
| 战斗主界面 | `battle` | 读取战况并选择下一行动 | 战斗快照缺失转 `error`，可安全退出 | 当前不可用命令保留位置并解释 |
| 术法签 | `arts` | 查看灵力、效果并选术法 | 无可用术法时给出返回/切换队伍 | 灵力或规则限制时显示原因 |
| 战斗换位 | `switch` | 在战斗中选择可换精怪 | 无可换目标时说明并返回战斗 | 倒下或受限目标可见并解释 |
| 队伍页 | `party` | 查看局内队伍详情与次序 | 队伍异常为空时转 `error` | 不可调整位置时保持只读并说明 |
| 囊 | `bag` | 查看并使用局内物品 | 无物品时说明获得路径并可返回 | 不适用物品禁用并说明目标条件 |
| 目标选择 | `target` | 为行动选择合法目标 | 无合法目标时取消行动并返回 | 非法目标可见但不可选，并显示原因 |
| 收契 | `catch` | 选择镇物或放过 | 无镇物时突出“放过”并说明获得路径 | 不可收契时说明规则并允许继续 |
| 战后摘要 | `summary` | 阅读结算变化并继续 | 无变化也显示“本轮无变化” | 未满足领取条件的项目说明原因 |
| 商店/机缘 | `shop` | 比较并选择奖励 | 无可选项时提供安全继续 | 费用或条件不足时显示差额/条件 |
| 天时奇遇 | `omen` | 阅读影响并作出选择 | 无事件时安全返回主流程 | 未满足选项保留可见并说明条件 |
| 境域地图 | `map` | 查看路径并选择下一境域 | 无可达节点时转可恢复 `error` | 未开放节点显示连接与条件 |
| 失败结算 | `defeat` | 理解本局结果并回厅 | 无明细仍显示结果与回厅 | 无自然锁定；注入时仅禁用重复提交 |
| 胜利结算 | `victory` | 理解完成结果并回厅 | 无明细仍显示结果与回厅 | 无自然锁定；注入时仅禁用重复提交 |
| 孵化揭晓 | `hatch` | 查看新获得内容并确认 | 揭晓数据缺失转可重试 `error` | 动画可跳过；内容未就绪时保持等待说明 |

### 3.2 五态统一契约

- **normal：** 页面主任务、单一主行动、明确返回路径均可见；破坏性动作需要确认。
- **loading：** 保留页面骨架和上一次安全上下文；首个 `250 ms` 内无稳定结果则显示进度提示。禁止伪造百分比；超过 `10 s` 显示取消/重试。加载期间阻止重复提交，但允许安全返回。
- **empty：** 说明“为什么为空”“如何产生内容”“现在能做什么”；不得只放空插图。没有自然空态的页面把缺失必需数据升级为 `error`。
- **error：** 使用用户可理解的原因、重试、返回安全页三件套；日志可记录技术码，界面不显示堆栈。重试必须幂等，存档/领取/购买不得重复执行。
- **locked：** 内容位置稳定、条件可读、颜色之外另有图标或文字；禁用控件不响应提交。满足条件后原位刷新，不让用户重新寻找目标。

所有状态都必须有可自动定位的 `screenId`、`state`、主行动标签和可访问名称。状态变化通过同一个 ScreenModel 输入驱动，不允许渲染层自行猜测玩法状态。

## 4. 画布与响应式

### 4.1 竖屏主目标

- 设计画布固定为 `750×1334`，截图验收也使用此尺寸。
- 背景可越过安全区，正文、主行动和返回控件必须在安全区内。
- 8pt 网格；正文基线不小于 24 设计像素；主要按钮可见高度不小于 56，任何点击热区不小于 `44×44`。
- 长列表使用滚动，不通过压缩字号塞入一屏。弹层不得遮断唯一返回路径。

### 4.2 横屏可用

横屏验收画布为 `1334×750`。横屏不是放大或压扁竖屏，也不得只显示“请旋转设备”。

- AppShell 在宽高比大于 1 时启用横屏重排：主内容与辅助信息采用双栏或侧栏；背景允许裁切，角色与交互信息不得裁切。
- 标题/模式/初始/结算页将角色区与操作区并列；列表/详情页将导航与内容并列；战斗页保持战场为主区、术法竖签和工具为侧区。
- 主任务、返回、重试、设置、战斗全部命令在横屏可达；必要时滚动，不减小热区。
- 在 `1334×750` 和带安全区设备上不得重叠、越界、出现黑边或不可点击控件。

## 5. 三关键帧门

三张关键帧均为原创 `750×1334` 竖屏构图，路径固定为：

1. `docs/ui/keyframes/title.svg`：远景天光，中景城邑/山野，前景草叶；角色陪伴区；“新的旅途”为唯一一级行动。
2. `docs/ui/keyframes/starter.svg`：三只原创精怪卡、选中详情、灵性/费用信息、单一确认行动；立绘等比 contain 且透明底。
3. `docs/ui/keyframes/battle.svg`：中景敌我立绘与名牌，右侧竖列术法签，上方队伍/囊/镇物，底部战况文本；不得做成常见四格底栏。

**门禁：**

- **K1 构图门：** 三张关键帧同时具备正常态、文字层级、安全区和 44 热区标注；人工审查原创性与页面主任务。未通过不得开始 U1 presentation。
- **K2 引擎还原门：** 对应阶段在实际 Cocos 中以 `750×1334` 捕获截图；关键区域位置、层级、留白和角色比例与 K1 意图一致。静态稿不参与通过判定。
- **K3 双向与状态门：** 同页补齐 `1334×750` 及 loading/empty/error/locked 证据，差异有明确理由；三页均通过后才能进入 U10 总门。

## 6. 实际 Cocos 证据真源

### 6.1 截图

合格截图必须同时满足：

- 来自仓库根目录由 Cocos Creator 3.8.2 打开的实际预览或对应平台最终构建；画面中是本次代码和资源。
- 记录提交/变更 ID、平台、画布、设备像素比、页面、状态、种子、捕获命令或手工步骤与文件路径。
- 竖屏证据为 `750×1334`，横屏证据为 `1334×750`；每个产品面至少 normal，适用的四个系统状态均有证据。
- 浏览器替身、SVG、设计工具导出、旧截图、平台 preview pack 与 `.shots` 只能辅助诊断，必须标注“非验收证据”。

截图不得人工修补 UI 像素。只允许无损裁去窗口外框；裁切后必须保留完整游戏画布。

#### 6.1.1 逐张肉眼验收（强制）

**任何产出截图的验证，必须逐张用肉眼查看每张截图本身，不得只凭几何断言
（节点数、按钮尺寸、hosts 计数等）判定"渲染通过"。**

原因（2026-09-02 复盘）：曾有一轮验证只断言几何数据就判过，结果两类缺陷被长期掩盖——
(a) 新 UI 叠在旧入口界面之上、两层文字穿透；(b) 文案泄漏、主次按钮层级反、
列表项与主行动重复等布局缺陷。几何断言全过，肉眼一看即错。

据此，截图验收的操作要求：
- 生成截图后，逐张打开查看，确认：无叠加穿透、无占位残留、主次层级正确、
  文案是给玩家看的展示文本（不得泄漏 accessibleName 等内部字段）、留白合理。
- 几何断言只作为**补充**证据，不能替代肉眼查看。
- 若验证在无头环境，仍须把截图取回逐张查看；不能因"数据通过"跳过看图。

### 6.2 包体

- 分别检查微信和抖音小游戏的最终 Cocos 构建目录；必须存在平台入口与配置文件。
- 主包统计为最终目录总字节数减去已声明分包与 remote 目录；每个平台主包 `≤ 4,194,304` 字节。
- 原始立绘、非首屏音频和大图优先 remote/分包；不得用占位文件、空文件或仅日志脚本伪造通过。
- 报告同时列出主包、每个分包、remote、总文件数和最大 20 个文件。

## 7. 可访问性

1. 正文与背景对比度至少 `4.5:1`，大字至少 `3:1`，重要非文本边界/焦点至少 `3:1`。
2. 点击热区至少 `44×44` 设计像素，紧邻危险操作间距至少 16；可见图标小于热区时仍由透明热区承载。
3. 信息不得只靠色相、闪烁或音效表达；灵性、增减益、选中、锁定均同时有文字/形状。
4. 所有控件有可读名称、角色、当前值与禁用原因；键盘/手柄模拟环境存在确定焦点顺序和可见焦点。
5. 设置提供“减少动效”；启用后移除循环漂浮、强闪、镜头震动，将必要过渡压到 `≤150 ms`。任何模式均不使用每秒超过 3 次闪烁。
6. 正文不烘焙进位图；文本放大至 200% 时允许滚动，不截断主行动和错误信息。
7. 音效不是唯一反馈；关键行动同时提供视觉确认。横竖屏保持同等可达性。

## 8. 性能预算

以指定中档验收设备连续运行 3 次，取中位数；设备、系统、构建 ID 和采样工具必须入档。

| 指标 | 预算 |
|---|---:|
| 冷启动至标题可交互 | `≤3.0 s` |
| 本地页面切换至可交互 | `≤500 ms`；超过 `250 ms` 显示 loading |
| 常规 UI 帧率 | 95% 采样 `≥50 FPS`，不得连续 1 秒低于 30 FPS |
| 标题/列表 Draw Call | `≤80` |
| 战斗峰值 Draw Call | `≤120` |
| 运行 15 分钟后 UI 峰值内存 | `≤180 MiB`，回厅后较首轮基线增长 `≤10%` |
| 单次 ScreenModel 更新至呈现 | p95 `≤50 ms` |
| 微信主包 / 抖音主包 | 各 `≤4 MiB` |

性能未达标时不得通过阶段退出门；只能记录真实差距、复现步骤和下一阶段前必须完成的修复，不得降低采样压力或隐藏状态。

## 9. 验收方法

### 9.1 自动验收

- 页面矩阵覆盖 `LOBBY_SCREENS`、`RUN_SCREENS`、全部 `TOUR` stop，并额外覆盖 `party` 与契录列表/详情体验。
- 每个产品面至少有 normal/loading/error 状态测试；表中定义自然 empty/locked 的页面必须有对应测试；注入所有五态不得抛错。
- presentation 的 ScreenModel 快照不依赖 Cocos；core 保持不导入引擎模块。
- 状态切换、重复重试、旋转、返回、恢复存档均有失败先行测试。
- 最终构建审计拒绝入口缺失、主包超限和占位产物。

### 9.2 人工 Demo

每阶段 Demo 使用固定种子，从阶段入口完成主任务；现场切换五态、竖横屏和减少动效。Demo 必须由实际 Cocos 运行，不接受录屏替代现场可操作版本；可附录屏作为证据。

### 9.3 产品化总退出门

U11 只有同时满足以下条件才完成：

1. 25 个产品面均可从真实流程或审计入口到达，主任务与返回路径有效。
2. 页面/状态/方向矩阵无缺项，三关键帧 K1–K3 全部通过。
3. 两平台实际最终构建主包均不超过 4 MiB，性能预算全部达标。
4. 对比度、热区、非颜色表达、减少动效、焦点与文本放大检查通过。
5. 实际 Cocos 截图元数据齐全，无替身证据冒充；横屏可完成一局核心流程。
6. `pnpm test`、`pnpm check:forbidden`、UI 审计、构建审计和相关 Python 测试均通过；修改 core 后已 `pnpm sync:core`。
7. clean-room 复核确认没有第三方素材、角色、文案、具体布局或动效时间线复制。

## 10. 变更纪律

- U0 只建立文档、基线与验收工具；U1 才允许开始 presentation/AppShell 实现。
- 每个 U 阶段开工前必须有独立详细计划，包含准确文件路径、失败测试、最小实现、验证命令、Demo 与退出门。
- 一次只允许一个 U 阶段处于实施中；上一阶段未通过退出门，不得预做下一阶段代码或资源。
- 范围变化先改本规格并复核路线图，不在实现中口头扩项。
