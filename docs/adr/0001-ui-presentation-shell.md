# ADR-0001：保留 Cocos/core，引入 presentation 与 AppShell

- **状态：** Accepted
- **日期：** 2026-08-31
- **决策范围：** 明亮童话志怪 UI 产品化

## 背景

当前 Cocos 入口 `assets/scripts/Boot.ts` 同时承担启动、页面选择、节点创建、绘制、输入、存取、战斗 HUD 更新和局内命令编排。该方式曾适合快速建立可玩版本，但页面、五态、横屏、可访问性和实际截图验收继续增长后，会产生三个问题：

1. 页面视觉与玩法状态耦合，难以在不启动引擎的情况下验证 ScreenModel 和状态覆盖。
2. 页面生命周期、方向、安全区与弹层栈分散在命令式方法中，迁移时容易出现双重监听和重复提交。
3. 全量重写风险过高；如果没有逐页回退边界，任一页面问题都可能阻塞完整流程。

决策驱动因素按优先级为：保持现有玩法确定性；保留已验证的 Cocos 构建链；支持逐页迁移和回退；纯逻辑可测试；主包 `≤4 MiB`；不引入第三方实现或素材。

## 备选方案

### 方案一：继续扩展 Boot 命令式绘制

**优点：** 改动最少；短期能快速替换颜色、坐标和节点。

**缺点：** 单文件继续承担状态与呈现；五态和横屏会形成条件分支网；组件复用、无头测试、逐页证据和性能归因困难；回退只能回退整个入口。

**结论：** 不选。允许它在迁移期作为旧呈现适配器存在，不再承接新的产品化页面结构。

### 方案二：更换引擎

**优点：** 可以重新设计 UI 技术栈和编辑流程。

**缺点：** 需要重做构建、平台接入、资源导入、输入、性能基线与发布验证；与本轮只产品化 UI 的目标不成比例，且显著增加 clean-room、包体和进度风险。

**结论：** 不选。本 ADR 有效期内不得以 UI 迁移为由启动引擎替换。

### 方案三：保留 Cocos/core，引入 presentation 与 AppShell

**优点：** 保留玩法和平台投资；ScreenModel 可无头测试；AppShell 集中处理生命周期；可按页面路由迁移与回退；组件、状态和响应式规则可复用。

**代价：** 迁移期存在新旧两套 renderer；需要严格禁止双挂载、双监听和双状态源；需要维护 manifest 与适配器测试。

**结论：** 选择。

## 决策

采用四层边界：

1. **`packages/core`：领域与玩法。** 继续拥有规则、随机性、存档语义和命令结果；不得导入 Cocos 模块，不知道节点、颜色、坐标、动画或方向。
2. **presentation：产品面模型。** 纯 TypeScript 将 core snapshot、资源状态与产品状态规范化为只读 `ScreenModel`；输出 `screenId`、`state`、内容、可用动作、禁用原因和可访问语义。它不创建节点、不读设备 API、不计算玩法结果。
3. **Cocos renderer：呈现适配。** 将 ScreenModel 绑定到组件/prefab，负责视觉与输入事件上报；不得直接修改 core，也不得从标签文本反推命令。
4. **`AppShell`：组合根。** 唯一负责 screen manifest、页面宿主、弹层栈、viewport、安全区、资源生命周期、输入通道和新旧路由选择。AppShell 不包含页面坐标或玩法条件。

期望依赖方向为：

```text
Cocos renderer ──> presentation ──> packages/core
       │                  ▲
       └──── AppShell ────┘
```

事件反向流动时只传稳定 action ID 与参数：renderer → AppShell dispatcher → core command → 新 snapshot → presentation → renderer。任何页面都不得双向绑定可变 core 对象。

## 所有权与接口边界

### 状态所有权

- core 是玩法状态唯一所有者。
- AppShell 只拥有瞬时 UI 状态：当前路由、弹层栈、焦点、方向、资源 loading/error 与防重复提交标记。
- presentation 只做确定映射；相同输入必须产生结构相等的 ScreenModel。
- renderer 只拥有节点/动画句柄；销毁时必须解除全部监听和计时器。

### 资源边界

- 首屏壳、基础字体、必要图标可进入主包；原始立绘、非首屏音频和大图保持 remote/分包优先。
- renderer 通过资源句柄接收 ready/loading/error，不直接拼 remote URL。
- 资源错误映射为规格中的页面状态；不能因缺图改变玩法结果。
- 两个平台最终主包分别不得超过 `4,194,304` 字节。

### 测试边界

- core：规则与命令结果测试，不断言 Cocos 节点。
- presentation：每个产品面的 normal/loading/empty/error/locked、动作映射和快照测试，不启动引擎。
- AppShell：manifest、单 renderer 挂载、路由、方向、安全区、弹层与回退测试。
- renderer：组件契约、热区、绑定/解绑和实际 Cocos 截图；不重复测试玩法公式。
- 端到端：固定种子穿越真实页面，验证结果与迁移前一致。

## 迁移策略

迁移严格按 U0–U11，一次一阶段。

1. **U0 基线：** 记录页面、状态、关键帧、实际构建和性能；不改产品行为。
2. **U1 壳层：** 新增 presentation 接口、AppShell 与 screen manifest。旧 Boot 默认仍可承载全部产品页；新壳只运行诊断宿主。
3. **U2 基础件：** 建立无玩法判断的组件与五态容器，不迁移产品页。
4. **U3–U9 逐页切换：** manifest 对每个 `screenId` 指定 `legacy` 或 `presentation`。只有该页专项测试、实际 Demo 和回退测试通过后才能将默认值切到 `presentation`。
5. **U10 收口：** 全页面完成横屏、可访问、性能和包体门；旧路径仍可通过全局开关恢复。
6. **U11 决策：** 验证完整旅程与回退。旧 Boot 的删除必须是 U11 之后单独计划；在没有两个稳定发布窗口证据前保留薄适配器。

迁移过程中不搬动玩法代码来“方便 UI”，不更改存档结构，不批量改资源 ID。若 ScreenModel 暴露不足，先新增只读 core 查询或 adapter，并用迁移前后等价测试钉死。

## 回退策略

### 逐页回退

screen manifest 为每页保留稳定 renderer 选择。出现以下任一情况，立即将受影响页切回 `legacy`：主任务不可完成、重复提交、存档结果变化、实际 Cocos 崩溃、横竖屏阻断、性能硬门失败。回退不迁移或转换 core 状态；在同一 snapshot 上卸载新 renderer，再挂载旧 renderer。

### 全局回退

AppShell 提供构建期默认值与受控运行时开关，使全部页面走旧呈现。全局回退必须：

1. 先停止输入分发；
2. 销毁当前 renderer 并解除监听；
3. 保留 core 实例和当前 snapshot；
4. 挂载旧呈现；
5. 恢复输入并记录一次结构化回退事件。

不得同时隐藏新 renderer、显示旧 renderer；隐藏不等于销毁，会造成双监听。

### 数据回退

本迁移不改变存档 schema、服务器协议或 core 命令，所以不设计数据降级脚本。一旦实现需要数据迁移，必须暂停当前 U 阶段并新建 ADR；在此之前不得上线该变化。

## 失败与恢复边界

- presentation 映射失败：进入可恢复 error 壳，记录 `screenId` 与技术码，允许重试或逐页回退。
- renderer 创建失败：AppShell 销毁半成品并逐页回退；不得保留部分监听。
- 资源失败：保留布局和文本，给出重试/返回；不能创建虚假玩法数据。
- core 命令失败：由 core 结果映射为 error/locked；renderer 不自行补偿。
- 方向变化：AppShell 只更新 viewport model；页面 state 和尚未提交的选择保持不变。

## 明确边界

本 ADR **允许**：新增 presentation、AppShell、renderer adapter、screen manifest、纯 UI token/prefab、审计与测试；为只读呈现增加最小 core selector。

本 ADR **不允许**：换引擎；重写玩法流；修改随机结果、数值、存档/协议；让 core 依赖 Cocos；一次切换全部页面；在迁移中顺手删除旧呈现；把第三方实现、布局或素材带入仓库。

## 后果

### 正面

- 页面五态和动作映射可以快速无头验证。
- 横屏、安全区、输入和生命周期有单一责任点。
- 产品页可小步迁移，失败时不丢失当前 core 状态。
- 实际 Cocos 证据可按 screenId/state/viewport 稳定归档。

### 负面

- 迁移期维护两种 renderer，manifest 和等价测试不可省略。
- ScreenModel 增加一层类型与映射成本。
- AppShell 成为关键基础设施，需要严格限制职责，避免形成新的大文件。

## 合规与复核

- 所有视觉观察仅使用公开 URL，且只抽象层级、节奏与可用性原则。
- 禁止复制第三方素材、角色、文案、具体布局、图标轮廓和动效时间线。
- 每阶段退出前执行禁用词、范围、页面矩阵、实际构建与相关测试检查。
- ADR 的改变必须新建后续 ADR，不直接改写本决策历史。
